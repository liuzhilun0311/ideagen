# 小红书图文内容层次设计

## 目标

改进 IdeaGen 的系统默认提示词，使生成的知识图文在图片内具备清晰的信息层次和视觉主体，并使小红书发布文案具备可扫描的阅读节奏。图片与发布文案共享同一组事实，但不逐字重复。

## 范围

本次仅调整系统默认提示词及其测试：

- `backend/generation/prompts/outline_prompt.txt`
- `backend/generation/prompts/image_prompt.txt`
- `backend/generation/prompts/image_prompt_short.txt`
- `backend/generation/prompts/content_prompt.txt`
- 相关提示词契约测试
- 默认提示词备份和面向用户的变更说明

不修改 API 字段、数据库模型、已有作品数据结构、编辑器数据结构或用户自定义提示词。

## 用户与使用场景

主要用户在 IdeaGen 中输入主题，生成一套用于小红书发布的知识图文。用户希望：

- 图片不是标题加大段文字，而是有视觉主体、重点和容易扫读的信息组织。
- 同一套图片有统一风格，但各页布局不机械重复。
- 发布文案适合小红书阅读，可快速扫读，有重点和行动建议，不使用夸张的模板化“爆款黑话”。
- 图片内容与发布文案准确一致，不能在追求吸引力时新增事实、功效、价格、亲身经历或无依据的结论。

默认调性为专业、克制、清晰可信；允许少量符号、编号、emoji 和自然互动句，但不是固定套路。

## 方案比较与选择

### 方案 A：只强化“简洁、好看”的措辞

只在当前提示词中增加“少文字、多插画、注意层次”等要求。

优点是修改少；缺点是模型没有明确的页面结构选择规则，容易把“层次”理解成给一大段正文加边框或装饰，页面之间也容易重复。

### 方案 B：轻量格式化

要求大纲将正文拆为编号或短句，发布文案分段。

优点是能立即改善可读性；缺点是所有页面会趋向同一种“标题加列表”版式，无法稳定形成对比、流程、分类等不同的信息表达。

### 方案 C：内容组件化

大纲先为每页选择一个信息结构，再生成对应的上图文字与画面描述；图片提示词据此安排可见文字、视觉主体和阅读路径；发布文案以小红书的独立阅读结构重新组织同一组事实。

这是采用的方案。它在不变更现有页面文本格式和接口的前提下，向模型提供稳定的结构约束，并保留主题、页数和最终画风的自由度。

## 总体数据流

```text
用户主题、参考内容、参考图
        |
        v
大纲默认提示词
        |
        +--> 页面内容：上图文字 + 画面描述
        +--> 独立风格推荐元数据
        |
        v
用户最终选择图片风格
        |
        v
长图/短图默认提示词 + 最终风格约束
        |
        v
图片生成

同一套页面内容
        |
        v
小红书发布文案默认提示词
        |
        v
titles + copywriting + tags
```

风格推荐仅用于界面默认建议；图片模型最终只接收用户最终选择或自动推荐最终解析出的具体风格。页面结构不包含固定媒介、颜色或画风，以避免与最终风格冲突。

## 大纲提示词设计

### 输出兼容

继续输出既有的页面文本协议：

```text
[封面]
上图文字：
...
画面描述：
...

<page>
...
```

继续在末尾返回独立风格推荐元数据。该元数据不写入页面内容、发布文案或图片可见文字。

### 页面角色

大纲模型必须为每页选择一个最适合本页内容的页面角色，并通过“上图文字”和“画面描述”表达该角色；不新增机器可见的页面字段。

可用角色：

- 封面：主题、真实价值、明确视觉主体。
- 清单：2 至 4 个短要点，配合编号、图标或并列区域。
- 步骤：有明确先后关系的动作与必要判断条件。
- 对比：同一维度下的并列比较，双方尺度与标签顺序一致。
- 分类：按类别、场景、优先级或象限组织。
- 关系：组成、因果或流程关系；只有存在真实关系时才使用箭头或连线。
- 例子：用已提供或合理抽象的例子解释一个概念，不虚构个人经历。
- 总结：收束已讲内容，给出一个可执行的下一步，不新增结论。

### 页面层次约束

- 每页只使用一种主结构，不能在同一页同时堆叠列表、流程、表格和装饰框。
- 整套内容至少使用三种页面结构；相邻正文页优先采用不同结构。
- 封面和总结分别使用适合其目的的结构，不应被当作普通列表页。
- 正文页默认使用约 35 至 90 个汉字；内容必须保留的限定条件优先于字数限制，过密时增加页面而非缩小文字。
- 单个信息组件优先使用“短标签 + 一句具体解释”；正文页通常为 2 至 4 个组件。
- 每页只强调 1 至 2 个关键词、数字或结论。
- 每页必须有一个服务于内容的视觉主体，例如主体插图、实物组合、关系图、步骤路径、对比区域或分类布局。
- 画面描述要指出阅读顺序、视觉主体和信息关系，但不得含有最终画风、固定配色、无依据的数据或会被误印的制作说明。
- 上图文字只含应印在图片上的内容；不得写“请设计”“放置于左侧”“使用图标”等制作指令。

### 事实一致性

- 上图文字是图片和发布文案共同的事实来源。
- 名称、数字、步骤、单位、观点、限定条件和结论必须一致。
- 不能编造价格、地址、开放时间、统计、功效、人物证言、用户经历或来源。
- 画面描述中的人物、场景和道具只作为抽象视觉表达，不能被发布文案写成真实经历。

## 图片提示词设计

长图提示词与短图提示词必须使用同一套内容层次要求，以避免候选图、单页试风格和批量生成表现不一致。

### 内容解析

- “上图文字”是唯一需要渲染到图片中的文字来源。
- “画面描述”只作为视觉设计输入，不应作为图片文字出现。
- 对旧作品缺少分区的页面：标题、正文、要点可作为可见文字；背景、配图建议、排版说明只能作为视觉指令。
- 结构角色、结构名称、模型内部标记、风格推荐元数据和制作说明不得成为可见文字。

### 版式规则

- 先按本页页面角色确定一个主要布局，再安排标题、信息组件和视觉主体。
- 标题、组件和视觉主体必须有明确区域、对齐基线和阅读顺序。
- 视觉主体通常占页面可用面积约三分之一至二分之一；不得仅在文字周围添加无关装饰。
- 文字层级默认两级，信息较多时最多三级；不使用极小字体把内容硬塞进一页。
- 清单页使用清楚的编号、图标或并列分区；步骤页按顺序组织；对比页使用相同尺度；关系页的箭头必须有真实语义。
- 每页重点最多一至两个；装饰不得抢夺标题或关键信息的视觉优先级。
- 使用约 5% 的安全边距，正文不贴边、不跨越复杂主体。
- 整套共享最终风格指定的线条、材质、图标语言和视觉语气，但每页布局可根据角色变化。

### 风格冲突处理

- 用户最终选择的风格优先于主题、旧大纲、参考图或画面描述中出现的泛化画风词。
- 页面结构决定信息组织；最终风格决定插图、线条、材质、色彩倾向和视觉媒介。
- 风格不得改变上图文字、事实、数字、地点、步骤或结论。
- 内容准确性和文字可读性优先于风格装饰。

## 小红书发布文案设计

### 输出契约

继续返回：

```json
{
  "titles": ["标题一", "标题二", "标题三"],
  "copywriting": "发布正文，段落间使用\n换行",
  "tags": ["标签一", "标签二", "标签三"]
}
```

不修改前端编辑、保存和发布接口。

### 文案组织

发布文案以用户主题和页面“上图文字”为唯一事实依据，选择适合主题的表达结构：

- 教程：问题切入、步骤清单、执行提醒。
- 清单：适用人群、分类要点、选择建议。
- 科普：常见误区、核心解释、实际应用。
- 对比：选择难点、对比维度、适用情形。
- 建议：具体场景、建议及原因、可执行动作。

### 默认规则

- 开头用 1 至 2 句直接说明读者问题、主题价值或适用场景，不写“今天给大家分享”“你是否也……”等机械开场。
- 正文通常为 4 至 7 个短段落；连续内容超过约 3 行时必须拆分。
- 一篇正文只采用一种信息标记方式：`01 / 02 / 03`、`① / ② / ③` 或短横线，不能混用。
- 要点采用“短标签：具体解释”，不能只给口号。
- 图片展示重点，发布正文负责补充语境、衔接、解释和执行建议，不逐页照抄图片标题。
- 结尾优先给一个容易执行的下一步；仅在主题确实适合时增加一个自然互动问题。
- emoji 默认 0 至 3 个，仅用于段落引导或重点提示；医疗、法律、财务及严肃风险主题默认不使用。
- 标题输出三个实质不同的备选：直接说明主题、指出具体问题、突出页面中可支持的价值。
- 单个标题通常不超过 25 个汉字；不使用无依据的夸张承诺。
- 标签输出 3 至 6 个，覆盖核心主题、使用场景和目标人群；不加 `#`，不堆无关热词。

### 事实与语气约束

- 不新增图片未支持的事实、价格、营业时间、统计、功效、人物证言、亲测经历或确定性承诺。
- 图片画风不决定文风；漫画、摄影、手绘等均以用户主题和目标读者决定语言。
- 避免“谁懂啊”“绝绝子”“一定要收藏”等模板化黑话。
- 语言专业、自然、具体、可信；不使用 Markdown 标题、表格、代码围栏或设计说明。

## 兼容与迁移

- 默认提示词是实时读取的系统资源，更新后新生成任务直接使用新版默认提示词。
- 管理员已经手动修改过的系统默认提示词按现有机制保留其当前内容；本次不会通过程序覆盖运行环境中已保存的自定义内容。
- 用户创建、复制、排序或共享的提示词不受影响。
- 已有作品不需要迁移。旧页面按既有标题、正文、要点和视觉说明的兼容规则生成。
- 已有发布文案不重新生成、不覆盖手工修改内容。
- 在修改仓库的默认提示词前，创建可读的文本备份，便于比较与回退。

## 错误处理

- 模型未严格输出页面结构时，仍由现有页面解析器保存原始页面文本；图片提示词按“上图文字/画面描述/旧格式”规则降级处理。
- 模型返回错误 JSON 时，继续使用现有 `ContentService._parse_json_response` 的代码块、最外层 JSON 和原始 JSON 三级解析策略。
- 不对历史文本进行自动重写，不因无法识别角色而删除页面内容。

## 测试与验收

### 自动测试

- 四个默认提示词均可用当前占位符成功格式化，且不保留未替换的必需占位符。
- `content_prompt.txt` 中 JSON 示例的花括号被正确转义，不会破坏 Python `str.format`。
- 长图与短图提示词都包含“上图文字可见、画面描述不可见”的约束和完整页面上下文。
- 大纲提示词包含页面角色、结构多样性、内容组件和视觉主体规则。
- 图片提示词包含单主结构、可读性、视觉主体和最终风格优先级规则。
- 发布文案提示词包含小红书分段、单一编号体系、标题差异、标签限制和事实边界。
- 现有提示词格式契约测试继续通过。

### 集成验证

- 运行后端生成与提示词相关测试。
- 运行完整后端测试集。
- 运行前端测试、应用类型检查、测试类型检查和生产构建。
- 运行 `python manage.py makemigrations --check --dry-run`，确认提示词变更未意外引入数据模型变更。
- 运行 `git diff --check`，确认没有空白错误。

### 人工检查

对四个格式化后的默认提示词进行检查，确认：

- 结构标签和制作说明不会要求渲染到图片中。
- 画面描述不与最终画风约束冲突。
- 发布文案不要求复制图片中的整段文字。
- 新旧格式兼容规则均明确。

不进行真实付费模型调用、图像 OCR 验证或对特定上游模型输出质量的保证。提示词能提高结构约束与默认表现，但不同模型的最终文字渲染能力仍受上游模型限制。
